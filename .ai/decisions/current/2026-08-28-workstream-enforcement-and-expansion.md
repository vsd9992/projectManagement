# Decision: Enforce workstream membership at the API layer; expand it only via Change Order approval

**Decision**: Closes the gap flagged as risk #7 during M6 (a project's enabled-workstream set was descriptive, not a guardrail):
- **Enforcement**: `api::authz::require_project_workstream(txn, project_id, workstream)` is called alongside the existing role check at the *root* creation endpoint for each workstream-specific entity family — `design_asset` (Design), `production_task` (Manufacturing), `purchase_order` (Procurement), and `site_task` / `daily_log` / `punch_list_item` / `site_query` (Site Execution, four independent root endpoints, not children of `site_task`). It is **not** applied to reads/lists, to children of an already-gated root (e.g. `design_revision` — its parent couldn't exist without the check already passing), or to project-level machinery that isn't workstream-specific (`lead`, `quotation`, `change_order`, `invoice`, `milestone` — these apply to a project regardless of which workstreams it has enabled, consistent with `architecture.md`'s "BOQ linked to WBS, WBS items each tagged to a workstream" — the tagging is per-line-item, not per-project-level-entity, and no WBS entity exists yet to carry that tag).
- **Expansion**: the only way to add a workstream to an already-existing project is via Change Order approval. `CreateChangeOrderRequest` gained `add_workstreams: Vec<WorkstreamType>` (optional, alongside `line_items` — a Change Order can now carry BOQ changes, workstream additions, or both; at least one of the two is still required). Requested workstreams are recorded in a new `change_order_workstreams` table at creation time (rejected up front if already enabled on the project) and only take effect — inserted into `project_workstreams` — once the client approves the change order, in the same transaction as any BOQ re-baseline. A workstream-only Change Order (no line items) skips quotation re-baselining entirely rather than emitting a no-op quotation version.

**Basis**: Direct user request, made when reviewing the M6 finding on risk #7: "enforce workstream membership at the API layer and if scope needs to be changed (let's say site work needs to be included) then we can do that right?" — followed by an explicit choice, via a clarifying question, for the Change Order path over a plain internal toggle: *"Via Change Order approval (recommended) ... matches workflows.md's own 'client adds a room' scenario, and reuses the approval trail you already have."*

**Why the Change Order path over a bare toggle**: `workflows.md`'s own Scenario 3 already describes a mid-project scope change (e.g. "client adds a room") going through a Change Order with client approval. Enabling a new workstream is exactly that kind of event in practice — it's client-driven scope growth, not an internal correction — so routing it through the mechanism that already has an approval trail, audit attribution, and a single well-tested transaction boundary was preferred over building a second, parallel "just toggle it" endpoint with its own authorization story.

**Consequences/constraints**:
- Enforcement was deliberately scoped to *creation* of workstream-specific entities, not blanket-applied everywhere a `project_id` appears — over-applying it (e.g. to every list/read endpoint) would have been unrequested scope, not a fix for what risk #7 actually described.
- No endpoint removes a workstream once enabled — enforcement is a floor, not a toggle in both directions. Not requested, and not needed for MVP.
- `entity::workstream_type::WorkstreamType` gained a `Hash` derive (purely additive, needed to dedupe against a project's existing `project_workstreams` in a `HashSet`).
- New migration `m20260828_000008_add_change_order_workstreams` adds the `change_order_workstreams` table (tenant-scoped, RLS-enabled, unique on `(change_order_id, workstream_type)`) — requires the standard grants re-run against every database after migrating (see `AGENTS.md`).
