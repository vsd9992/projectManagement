# Decision: RBAC implemented as handler-level checks, keyed on business-unit membership + role

**Decision**: Every internal-facing endpoint now calls `api::authz::require_business_unit_role` (or `require_project_business_unit_role`, which resolves the business unit via the target's `project_id` first) before acting. List endpoints filter to `authz::accessible_business_units` instead of returning the whole tenant. Enforcement is **handler-level Rust code**, not a PostgreSQL RLS policy — chosen specifically to avoid touching `client_portal.rs`, whose access model (client_id matching, not role) is separate and already verified. Role mapping:
- **Sales & Design** (leads, quotations, design assets/revisions, change orders) → `sales_design`
- **Delivery** (purchase orders, production tasks, site tasks/dependencies, daily logs, punch list, site queries) → `delivery`
- **Finance** (invoices) → `finance`
- **Membership only, any role** (projects, milestones) → multiple roles legitimately touch these

Two supporting pieces landed alongside this: `POST /business-units/:id/roles` (role assignment — didn't exist before; without it there was no way to test or use RBAC at all), and `POST /users` (creates a second internal user in the *caller's own tenant* — signup previously could only create a brand-new tenant, so a tenant could never actually have more than one internal user, making "separate teams per business unit" impossible to exercise).

**Basis**: Direct follow-up to `.ai/decisions/current/2026-08-28-no-rbac-enforcement-yet.md` (archived — this decision supersedes it), raised during a pre-M6 risk/decision review where the user chose to fix this before running M6 rather than after.

**Why**: The gap wasn't just "role isn't checked" — business-unit *membership* wasn't checked either, so a tenant with multiple branches had zero team separation despite that being a stated requirement from the original design. Handler-level checks (vs. RLS) were chosen after recognizing that RLS-based enforcement would need an explicit bypass for the Client Portal (which authenticates a different principal type — `client_user`, not `user` — and is scoped by `client_id`, not business unit), and building that bypass correctly was a real risk to already-verified, money-sensitive invoice-visibility code. A few extra database round-trips per request was judged the safer tradeoff.

**Bundled alongside this** (same review, same fix pass, not strictly RBAC but the same "close the gap between what auth claimed and what it does" motivation): `POST /users/:id/revoke-sessions` deletes every session for a target user. The session-based-auth decision's own stated rationale for choosing sessions over JWT was "instantly kill a departing employee's access" — but no endpoint actually did that until now; only self-logout (one session) existed. Verified live: an active session was confirmed working, revoked, and confirmed dead on the very next request with the same cookie.

**Consequences/constraints**:
- Every new internal endpoint added from here on must call the appropriate `authz::` check — this is not automatic (unlike RLS, which would have applied itself). Forgetting it is a silent regression back to the old gap.
- List endpoints must filter by `accessible_business_units`, not just `find().all()` — also not automatic.
- **Still open**: there is no distinct admin/owner role. Anyone in a tenant can assign any role to anyone (`POST /business-units/:id/roles`), create business units, add teammates (`POST /users`), or revoke any other user's sessions (`POST /users/:id/revoke-sessions`). This is a real, smaller remaining gap — tracked, not silently accepted as permanent.
- Verified with a real integration-test suite (`backend/api/tests/authz.rs`, run against a dedicated `project_management_test` database, not the dev-server's fixture data) covering: role-gated creation (wrong role → 403, correct role → 200) for one endpoint per role group, and cross-business-unit visibility scoping (list filtering + direct-access denial). Also verified against the *existing* M1–M5 dev-server data: a pre-existing user with zero role assignments was correctly locked out (empty list, 403 on create) rather than erroring, and assigning the role retroactively restored full access — confirming the retrofit is safe for already-existing tenants, not just fresh ones.
