# Decision: Two-tier admin model — tenant admin (per-tenant) and platform manager (above all tenants)

**Decision**: Adds two account tiers on top of the RBAC/business-unit-scoping work:
- **Tenant admin** (`users.is_tenant_admin`): authority across the *whole* tenant — every business unit, not just one team's. The signing-up user becomes their tenant's founding admin automatically; only an existing admin can promote/demote another user, and the last remaining admin of a tenant cannot be demoted (no path to a tenant locking itself out of its own admin tier). `api::authz`'s checks (`require_business_unit_role`, `require_project_business_unit_role`, `accessible_business_units`) all short-circuit for tenant admins — this is also where "tenant owners get roll-up visibility across all business units," a requirement from the very first design session that was never actually built, finally lands. Org-management actions (create business unit, assign roles, add teammates, revoke another user's sessions) are now tenant-admin only, closing the exact gap flagged as the remaining risk after the RBAC pass.
- **Platform manager** (`platform_admins` / `platform_admin_sessions`, both new tables): operates *above* every tenant, not a member of any of them. Scope is deliberately narrow — pause (reversible), resume, or soft-delete (terminal, no undelete endpoint) a tenant's lifecycle. No access to tenant business data (leads, quotations, financials): nothing in `routes::platform` ever queries a tenant-scoped table. Kept on completely separate auth infrastructure (its own tables, its own session cookie name `platform_session_token`) rather than extending the tenant `sessions` table with a third principal type — a platform manager session has no natural `tenant_id`, and mixing "who can pause/delete a customer's account" auth with tenant auth infrastructure is exactly the kind of shared-blast-radius decision worth avoiding deliberately. No self-service signup for this tier (too privileged); bootstrapped only via a CLI (`backend/api/src/bin/create_platform_admin.rs`), password read from an env var, never a CLI arg, so it never lands in shell history or a process listing.

A paused or deleted tenant is locked out at the session level — both `AuthenticatedUser` and `AuthenticatedClientUser` check tenant status on every request, not per-handler, so there's no way to forget the check on a new endpoint.

**Basis**: Direct user request, made during the same pre-M6 review that produced the RBAC/business-unit-scoping decision: "we need to add distinct admin/owner role. One application manager... who can pause/resume/delete the tenant... and one admin per tenant to manage their organization."

**Why**: The RBAC pass left "any tenant user can manage the org" as an explicit open risk. Splitting admin authority into a per-tenant tier (managing one's own organization) and a platform tier (managing tenant lifecycle across the whole SaaS) matches the actual shape of the ask and keeps the two blast radii separate — a compromised or malicious tenant admin can do damage only within their own tenant; a platform manager can affect tenant lifecycle but never see tenant business data.

**Consequences/constraints**:
- Existing tenants created before this migration had `is_tenant_admin = false` for every user (the column default), which would have permanently locked them out of org-management actions with no path forward via the API. A follow-up migration (`m20260828_000007_backfill_tenant_admin`) promotes each existing tenant's earliest-created user to admin — verified against the live dev-server data (both pre-existing tenants correctly backfilled, confirmed the retroactively-admin user could immediately create a business unit).
- Platform actions (pause/resume/delete) are attributed in `audit_log` as `Actor::System` with `platform_admin_id` recorded in the JSON payload, not a queryable actor column — a third actor-attribution FK (alongside `actor_user_id`/`actor_client_user_id`) was judged not worth a further schema change for a rare, high-privilege action class. This was caught and fixed *during* this same pass — the first version of `routes::platform` didn't audit-log tenant transitions at all, verified missing via a live audit_log query, then fixed and re-verified.
- Verified with 2 new integration tests (`org_management_is_tenant_admin_only`, `platform_admin_can_pause_resume_delete_tenant`) alongside the 4 existing RBAC tests, all rewritten to use a non-admin teammate account for role-gated assertions (the signing-up owner is now always a tenant admin and bypasses role checks by design, which would have made the original tests silently pass for the wrong reason). Also verified live against the dev-server's real tenant: paused it, confirmed the owner's active session was immediately locked out with a clear `"tenant is paused or has been deleted"` message (not a generic 403), resumed it, confirmed access returned.
