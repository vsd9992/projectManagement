## Phase 2 — Execution (MVP: Turnkey Interiors, full depth)

- **M1 — Foundation**: tenancy/auth/org model (Tenant, Business Unit, User, Role), Project entity with enabled Workstreams, base entity CRUD + Audit Log wired in from the start (per risk #5 in `risks.md`). **Status: complete and verified.**
  - Implementation: Rust/Axum/SeaORM/SQLx/PostgreSQL workspace (`backend/`) — migration crate (core schema + RLS policies), entity crate, Axum API with session-based auth (signup/login/logout), business unit and client CRUD, and project creation with an arbitrary workstream subset.
  - Verification (run 2026-08-27 against a live PostgreSQL instance on the dev server, not just compiled): signed up a tenant, created 2 business units and a client under it; created a turnkey project with 3 workstreams (design, procurement, site_execution) and a separate pure-manufacturing project with 1 workstream (manufacturing) — confirming the composable workstream model handles both shapes on the same entity. `audit_log` row counts matched every create exactly (2 tenants, 2 users, 2 business units, 1 client, 2 projects, 4 project_workstreams). RLS isolation confirmed at both the API level (a second tenant's session sees zero of the first tenant's business units/projects) and directly at the database level (the `app_user` role sees 0 rows with no tenant context set, and only the correct tenant's rows once `SET LOCAL app.tenant_id` is issued).
  - One real bug found and fixed during verification: the tenant-creation audit-log entry referenced `actor_user_id` before the user row existed in the same transaction, violating the FK constraint — fixed by recording that specific entry with no actor (self-signup has no prior actor for the tenant-creation event).
- **M2 — Sales & Design workstream**: Lead → Quotation (versioned BOQ) → Design (versioned drawings/specs) → Client Approval loop. **Status: complete and verified.**
  - Implementation: `leads`, `client_users` (extending sessions to carry either an internal-user or client-user principal — the Client Portal auth mechanism originally slated for M5 was pulled forward here since design approval genuinely needs a real authenticated client actor, not an internal proxy), `quotations`/`quotation_line_items` (versioned BOQ), `design_assets`/`design_revisions` (versioned, with approve/reject). `audit_log` extended with `actor_client_user_id` so client decisions are attributed as precisely as internal-user actions.
  - Verification (run 2026-08-27 against the live dev-server database): created a lead, converted it to a project (and confirmed re-conversion is rejected); created two quotation versions on that project with correct computed line-item amounts and intact version history; created a design asset with two submitted revisions; created a client-portal login, logged in as that client, and confirmed they see all their own projects but only their own; the client rejected revision v1 and approved v2 (confirmed a decided revision can't be re-decided); a second client under the same tenant was confirmed unable to see or act on the first client's project/revision (404, not a status leak) — proving the extra client_id filtering layer on top of RLS actually works, not just tenant isolation. `audit_log` correctly attributed every internal action to `actor_user_id` and both client decisions to `actor_client_user_id`, never both.
- **M3 — Change Orders**: scope change entity, links to the BOQ (quotation), client-approval-required flow, re-baselining. **Status: complete and verified.** Schedule re-baselining is explicitly out of scope here — no Schedule entity exists yet (Schedule Task/Dependency/Milestone are later work); this milestone covers budget/BOQ re-baselining only, as the requirements/architecture docs describe it.
  - Implementation: `change_orders`/`change_order_line_items` (each line either a new item, a modification of an existing quotation line, or a removal — the mechanism covering scope extension and reduction in one model). Added the quotation approve/reject endpoints that M2 deliberately deferred (`/client/quotations/:id/approve|reject`), since a Change Order needs a genuinely *approved* BOQ to apply against. On Change Order approval, the base quotation's lines are carried over except where touched, modifications/additions are applied, removals are dropped, and the result becomes the next quotation version (`status='approved'`) — the prior baseline and any other non-terminal quotation for the project are marked `superseded`, keeping "at most one approved quotation per project" an enforced invariant.
  - Verification (run 2026-08-28 against the live dev-server database): a Change Order against a *non-approved* (superseded) quotation was correctly rejected before any client involvement. Approved a quotation (v2) via the client, confirmed the prior version was superseded. Created a Change Order modifying one line's quantity and adding a new line; `cost_impact` computed correctly (85000.00 = delta from the modification + full amount of the addition). Client approved it: a new quotation v3 was created with exactly the expected re-baselined line items and correct amounts, v2 was superseded, and `new_quotation_id` was populated on the change order. Re-approving the same (already-approved) change order was correctly rejected. A second Change Order (a pure removal, cost_impact -40000.00) was rejected by the client and confirmed to leave v3 completely untouched — rejection has no side effects on the baseline. `audit_log` shows explicit before/after JSON for both the approval (`status: pending_client_approval → approved`, `new_quotation_id` populated) and the rejection (`status: pending_client_approval → rejected`).
- **M4 — Delivery workstreams**: internal-facing Procurement (POs to vendors), simplified Manufacturing "production task" tracking, Site Execution (tasks, daily logs, punch list, basic RFI/query log). **Status: complete and verified.**
  - Implementation: `vendors`/`purchase_orders`/`purchase_order_line_items` (PO lines optionally link back to the originating `quotation_line_item`), `production_tasks` (simplified single-status tracking, per the MVP-depth decision — no shop-floor/QC/dispatch), `site_tasks` + `site_task_dependencies` (explicit task-to-task links — scoped to site-task-to-site-task for M4; a richer cross-entity graph, e.g. a task depending on a PO delivery, is future work once Schedule entities exist), `daily_logs`, `punch_list_items`, and `site_queries` (basic RFI/query log — full formal submittal/transmittal routing is deferred to the standalone Civil vertical). All internal-facing only, consistent with the no-vendor-portal MVP decision.
  - Verification (run 2026-08-28 against the live dev-server database): a PO was raised with a line item and marked delivered; re-delivering the same PO was correctly rejected. Two site tasks were created and linked ("Install workstations" depends on "Electrical rough-in"); a self-dependency attempt was correctly rejected; both tasks were progressed to "done" via status updates. A punch list item was raised and closed; re-closing was correctly rejected. Production task and site query flows (create, status/answer transitions, invalid-status rejection) also verified. `audit_log` counts matched every create and status-changing update exactly across all nine new entity types — no gaps.
- **M5 — Billing & Client Portal**: milestone-based billing (generic engine, India rule profile), minimal Finance role (raise/track invoice, mark paid, track retention). Client Portal auth/access itself was already built in M2 — this milestone extends it with invoice visibility, not portal login from scratch. **Status: complete and verified.**
  - Implementation: a minimal `milestones` entity (just enough for milestone-based billing to hook into — not the full Schedule Task/Dependency/Milestone graph, which is later work) and `invoices`, computed via a pluggable `RegionProfile` trait in `api/src/billing.rs` (`profile_for(tenant.region_profile)` — a new `tenants.region_profile` column, defaulted to `"india"`). `IndiaGstProfile` computes GST (18%) and GST TDS (2%) on the taxable base amount; retention is a per-invoice percentage (no billing-settings entity yet). An invoice can only be raised against a *completed* milestone. Mobilization-advance recovery is explicitly deferred — it needs a running per-project advance balance that isn't modeled yet, and wasn't required by verification. "Finance role" was interpreted as the capability being built (invoice management), consistent with how "Sales & Design" and other workstreams were built in M2–M4 — no new role-based access-control enforcement was added (any authenticated internal user can raise/mark-paid), matching the precedent set by every prior milestone; RBAC enforcement remains a deferred cross-cutting concern across all workstreams, not something introduced piecemeal for Finance alone.
  - Verification (run 2026-08-28 against the live dev-server database, with figures hand-computed independently first): raising an invoice against a *pending* milestone was correctly rejected; after completing the milestone, an invoice with base_amount=100000, retention_percent=5 produced gst_amount=18000.00, gst_tds_amount=2000.00, retention_amount=5000.00, gross_amount=118000.00, net_payable=111000.00 — an exact match to the hand-computed values. Marked paid; re-marking paid was correctly rejected. The client viewed the invoice (with full correct figures) via the portal; a second client under the same tenant got a 404 (not a leak) probing the same project's invoices, extending the same cross-client isolation pattern verified in M2/M3 to money-relevant data specifically. `audit_log` counts matched every create and status-changing update exactly.
- **M6 — MVP verification**: run the three scenario walkthroughs from `workflows.md` end-to-end against the actual implementation (not just on paper); confirm no forced workarounds.
