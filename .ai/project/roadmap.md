## Phase 2 — Execution (MVP: Turnkey Interiors, full depth)

- **M1 — Foundation**: tenancy/auth/org model (Tenant, Business Unit, User, Role), Project entity with enabled Workstreams, base entity CRUD + Audit Log wired in from the start (per risk #5 in `risks.md`). **Status: complete and verified.**
  - Implementation: Rust/Axum/SeaORM/SQLx/PostgreSQL workspace (`backend/`) — migration crate (core schema + RLS policies), entity crate, Axum API with session-based auth (signup/login/logout), business unit and client CRUD, and project creation with an arbitrary workstream subset.
  - Verification (run 2026-08-27 against a live PostgreSQL instance on the dev server, not just compiled): signed up a tenant, created 2 business units and a client under it; created a turnkey project with 3 workstreams (design, procurement, site_execution) and a separate pure-manufacturing project with 1 workstream (manufacturing) — confirming the composable workstream model handles both shapes on the same entity. `audit_log` row counts matched every create exactly (2 tenants, 2 users, 2 business units, 1 client, 2 projects, 4 project_workstreams). RLS isolation confirmed at both the API level (a second tenant's session sees zero of the first tenant's business units/projects) and directly at the database level (the `app_user` role sees 0 rows with no tenant context set, and only the correct tenant's rows once `SET LOCAL app.tenant_id` is issued).
  - One real bug found and fixed during verification: the tenant-creation audit-log entry referenced `actor_user_id` before the user row existed in the same transaction, violating the FK constraint — fixed by recording that specific entry with no actor (self-signup has no prior actor for the tenant-creation event).
- **M2 — Sales & Design workstream**: Lead → Quotation (versioned BOQ) → Design (versioned drawings/specs) → Client Approval loop. **Status: complete and verified.**
  - Implementation: `leads`, `client_users` (extending sessions to carry either an internal-user or client-user principal — the Client Portal auth mechanism originally slated for M5 was pulled forward here since design approval genuinely needs a real authenticated client actor, not an internal proxy), `quotations`/`quotation_line_items` (versioned BOQ), `design_assets`/`design_revisions` (versioned, with approve/reject). `audit_log` extended with `actor_client_user_id` so client decisions are attributed as precisely as internal-user actions.
  - Verification (run 2026-08-27 against the live dev-server database): created a lead, converted it to a project (and confirmed re-conversion is rejected); created two quotation versions on that project with correct computed line-item amounts and intact version history; created a design asset with two submitted revisions; created a client-portal login, logged in as that client, and confirmed they see all their own projects but only their own; the client rejected revision v1 and approved v2 (confirmed a decided revision can't be re-decided); a second client under the same tenant was confirmed unable to see or act on the first client's project/revision (404, not a status leak) — proving the extra client_id filtering layer on top of RLS actually works, not just tenant isolation. `audit_log` correctly attributed every internal action to `actor_user_id` and both client decisions to `actor_client_user_id`, never both.
- **M3 — Change Orders**: scope change entity, links to the BOQ (quotation), client-approval-required flow, re-baselining. **Status: complete and verified.** Schedule re-baselining is explicitly out of scope here — no Schedule entity exists yet (Schedule Task/Dependency/Milestone are later work); this milestone covers budget/BOQ re-baselining only, as the requirements/architecture docs describe it.
  - Implementation: `change_orders`/`change_order_line_items` (each line either a new item, a modification of an existing quotation line, or a removal — the mechanism covering scope extension and reduction in one model). Added the quotation approve/reject endpoints that M2 deliberately deferred (`/client/quotations/:id/approve|reject`), since a Change Order needs a genuinely *approved* BOQ to apply against. On Change Order approval, the base quotation's lines are carried over except where touched, modifications/additions are applied, removals are dropped, and the result becomes the next quotation version (`status='approved'`) — the prior baseline and any other non-terminal quotation for the project are marked `superseded`, keeping "at most one approved quotation per project" an enforced invariant.
  - Verification (run 2026-08-28 against the live dev-server database): a Change Order against a *non-approved* (superseded) quotation was correctly rejected before any client involvement. Approved a quotation (v2) via the client, confirmed the prior version was superseded. Created a Change Order modifying one line's quantity and adding a new line; `cost_impact` computed correctly (85000.00 = delta from the modification + full amount of the addition). Client approved it: a new quotation v3 was created with exactly the expected re-baselined line items and correct amounts, v2 was superseded, and `new_quotation_id` was populated on the change order. Re-approving the same (already-approved) change order was correctly rejected. A second Change Order (a pure removal, cost_impact -40000.00) was rejected by the client and confirmed to leave v3 completely untouched — rejection has no side effects on the baseline. `audit_log` shows explicit before/after JSON for both the approval (`status: pending_client_approval → approved`, `new_quotation_id` populated) and the rejection (`status: pending_client_approval → rejected`).
- **M4 — Delivery workstreams**: internal-facing Procurement (POs to vendors), simplified Manufacturing "production task" tracking, Site Execution (tasks, daily logs, punch list, basic RFI/query log). **Status: complete and verified.**
  - Implementation: `vendors`/`purchase_orders`/`purchase_order_line_items` (PO lines optionally link back to the originating `quotation_line_item`), `production_tasks` (simplified single-status tracking, per the MVP-depth decision — no shop-floor/QC/dispatch), `site_tasks` + `site_task_dependencies` (explicit task-to-task links — scoped to site-task-to-site-task for M4; a richer cross-entity graph, e.g. a task depending on a PO delivery, is future work once Schedule entities exist), `daily_logs`, `punch_list_items`, and `site_queries` (basic RFI/query log — full formal submittal/transmittal routing is deferred to the standalone Civil vertical). All internal-facing only, consistent with the no-vendor-portal MVP decision.
  - Verification (run 2026-08-28 against the live dev-server database): a PO was raised with a line item and marked delivered; re-delivering the same PO was correctly rejected. Two site tasks were created and linked ("Install workstations" depends on "Electrical rough-in"); a self-dependency attempt was correctly rejected; both tasks were progressed to "done" via status updates. A punch list item was raised and closed; re-closing was correctly rejected. Production task and site query flows (create, status/answer transitions, invalid-status rejection) also verified. `audit_log` counts matched every create and status-changing update exactly across all nine new entity types — no gaps.
- **M5 — Billing & Client Portal**: milestone-based billing (generic engine, India rule profile), minimal Finance role (raise/track invoice, mark paid, track retention). Client Portal auth/access itself was already built in M2 — this milestone extends it with invoice visibility, not portal login from scratch. **Status: complete and verified.**
  - Implementation: a minimal `milestones` entity (just enough for milestone-based billing to hook into — not the full Schedule Task/Dependency/Milestone graph, which is later work) and `invoices`, computed via a pluggable `RegionProfile` trait in `api/src/billing.rs` (`profile_for(tenant.region_profile)` — a new `tenants.region_profile` column, defaulted to `"india"`). `IndiaGstProfile` computes GST (18%) and GST TDS (2%) on the taxable base amount; retention is a per-invoice percentage (no billing-settings entity yet). An invoice can only be raised against a *completed* milestone. Mobilization-advance recovery is explicitly deferred — it needs a running per-project advance balance that isn't modeled yet, and wasn't required by verification. "Finance role" was interpreted as the capability being built (invoice management), consistent with how "Sales & Design" and other workstreams were built in M2–M4 — no new role-based access-control enforcement was added (any authenticated internal user can raise/mark-paid), matching the precedent set by every prior milestone; RBAC enforcement remains a deferred cross-cutting concern across all workstreams, not something introduced piecemeal for Finance alone.
  - Verification (run 2026-08-28 against the live dev-server database, with figures hand-computed independently first): raising an invoice against a *pending* milestone was correctly rejected; after completing the milestone, an invoice with base_amount=100000, retention_percent=5 produced gst_amount=18000.00, gst_tds_amount=2000.00, retention_amount=5000.00, gross_amount=118000.00, net_payable=111000.00 — an exact match to the hand-computed values. Marked paid; re-marking paid was correctly rejected. The client viewed the invoice (with full correct figures) via the portal; a second client under the same tenant got a 404 (not a leak) probing the same project's invoices, extending the same cross-client isolation pattern verified in M2/M3 to money-relevant data specifically. `audit_log` counts matched every create and status-changing update exactly.
- **Pre-M6 hardening — RBAC & business-unit scoping**: not part of the original roadmap; inserted after a risk/decision review surfaced that no role or business-unit-membership enforcement existed anywhere (`.ai/decisions/current/2026-08-28-rbac-business-unit-scoping-implemented.md`). **Status: complete and verified.**
  - Implementation: `api::authz` helpers (`require_business_unit_role`, `require_project_business_unit_role`, `accessible_business_units`) applied across every internal endpoint — sales_design for leads/quotations/design/change-orders, delivery for procurement/production/site-execution, finance for invoices, plain membership for projects/milestones. New supporting endpoints: `POST /business-units/:id/roles` (role assignment — didn't exist, so RBAC was previously untestable and unusable), `POST /users` (adds a second internal user to an existing tenant — signup could previously only create a brand-new tenant, so "separate teams per business unit" could never actually be exercised), `POST /users/:id/revoke-sessions` (kills all of a user's sessions — the auth decision's own stated rationale for choosing sessions over JWT, but never actually built until now). Also restructured the `api` crate into lib+bin so integration tests can drive the real router in-process.
  - Verification: a new integration-test suite (`backend/api/tests/authz.rs`, 4 tests) run against a dedicated `project_management_test` database — role-gated creation (wrong role → 403, correct role → 200) for one endpoint per role group, plus cross-business-unit visibility (list filtering + direct-access 403). Also verified against the *existing* M1–M5 dev-server data: the pre-existing tenant owner (zero role assignments) was correctly locked out (empty project list, 403 on lead creation) rather than erroring; assigning the role retroactively restored full access to their existing projects — confirming the retrofit is safe for already-existing tenants. Session revocation verified live: an active session confirmed working, revoked, and confirmed dead on the next request with the same cookie.
  - Explicitly left open at the time: no distinct admin/owner role — resolved immediately after, below.
- **Pre-M6 hardening — tenant admin & platform manager**: direct follow-up user request in the same review, closing the admin/owner gap left open above (`.ai/decisions/current/2026-08-28-tenant-admin-and-platform-manager.md`). **Status: complete and verified.**
  - Implementation: `users.is_tenant_admin` (per-tenant authority across every business unit — `api::authz` short-circuits for admins, which is also where "tenant owners get roll-up visibility across all business units" from the original design finally lands); org-management actions (create BU, assign roles, add teammates, revoke sessions) are now tenant-admin only; `POST /users/:id/admin` promotes/demotes, with a last-remaining-admin guard. Fully separate `platform_admins`/`platform_admin_sessions` tables and `platform_session_token` cookie (not an extension of tenant sessions — deliberate isolation for the most privileged account type) for a platform-manager tier that can pause/resume/soft-delete a tenant but never touches tenant business data. No self-service platform-admin signup — bootstrapped via `backend/api/src/bin/create_platform_admin.rs`, password via env var, never a CLI arg. A paused/deleted tenant is locked out at the session level for every one of its users. A follow-up migration backfills tenant-admin status onto each pre-existing tenant's earliest user, since the column default would otherwise have permanently locked already-existing tenants out of org management.
  - Verification: 2 new integration tests (`org_management_is_tenant_admin_only`, `platform_admin_can_pause_resume_delete_tenant`) alongside the 4 RBAC tests — all 6 passing, with the 4 original tests rewritten to use a non-admin teammate for role-gated assertions (the signing-up owner is now always tenant-admin and bypasses role checks by design). Verified live against the dev server's real tenant: paused it, confirmed the owner's active session was immediately locked out with a specific `"tenant is paused or has been deleted"` message, resumed it, confirmed access returned; confirmed a deleted tenant cannot be resumed. Verified the backfill migration against the real pre-existing dev-server tenants (both correctly promoted; the retroactively-admin owner could immediately create a business unit). One real gap caught *during* this same pass and fixed: the first version of the platform routes didn't write to `audit_log` at all for pause/resume/delete — caught by checking the live audit log, then fixed (attributed as `Actor::System` with `platform_admin_id` in the payload) and re-verified with a fresh pause/resume showing correct before/after entries.
- **M6 — MVP verification**: run the three scenario walkthroughs from `workflows.md` end-to-end against the actual implementation (not just on paper); confirm no forced workarounds. **Status: complete and verified.**
  - **Scenario 1 — Pure furniture order** (Manufacturing + Procurement only, no site work): a project was created with exactly those two workstreams enabled. Confirmed the composable model needs no workaround for a non-turnkey shape — BOQ, vendor/PO, and production-task flows all worked identically to the turnkey case, scoped to just the enabled workstreams. Observation (not a bug): nothing in the implementation *enforces* that an action stays within a project's enabled workstreams — e.g. a site task could technically be created on a project that never enabled Site Execution. The workstream set is currently descriptive/organizational, not a guardrail. Not required by `requirements.md`/`architecture.md` as written, so left as an observed gap rather than fixed under this milestone's mandate — worth a deliberate decision before Furniture/Civil verticals are built out, since those are exactly the projects most likely to hit it.
  - **Scenario 2 — Pure civil job** (Site Execution + light Design only): a project was created with just those two workstreams; RFI/site-query, punch-list, and daily-log flows all worked unmodified. Confirmed deviation already on record (`risks.md` risk #3): `workflows.md` says a pure civil job "likely uses the progressive RA-bill-style method rather than milestone billing," but only milestone-based billing is implemented — the same gap noted since M5, not new. No workaround was needed to exercise the scenario itself; billing depth just wasn't exercised beyond what M5 already covered.
  - **Scenario 3 — Turnkey interior with a mid-project scope change**: full lifecycle exercised on one project — lead → conversion (all 4 workstreams) → BOQ → client approval → design revision → client approval → vendor + PO → production task → site task — then a chain of three successive Change Orders against the live baseline (an addition, a removal, and a second addition), each requiring client approval and correctly re-baselining into the next quotation version (v2 through v5), with the prior version marked `superseded` each time and downstream workstream entities (the PO, production task, site task created earlier) confirmed untouched by every re-baseline. Confirms the core Scenario 3 claim from `workflows.md` — Change Orders re-baseline the BOQ and downstream workstreams remain independent — with one caveat already on record from M3: re-baselining is BOQ/budget-only, since no Schedule/WBS-task-graph entity exists yet, so "spawns new WBS items" and "re-baselines the schedule graph" aren't literally exercised, only the BOQ side.
  - Two real bugs found during Scenario 3 and fixed (per AGENTS.md Phase 3 rules — bug fixes, not baseline changes, since both contradict already-approved baseline behavior):
    1. **Lead conversion produced projects with zero workstreams.** `POST /leads/:id/convert` never accepted or created `project_workstream` rows, unlike direct project creation — silently violating the "one or more Workstreams" invariant in `architecture.md`. Fixed in [leads.rs](backend/api/src/routes/leads.rs): `ConvertLeadRequest` now takes a `workstreams` field, validated non-empty, and `project_workstream` rows are created in the same transaction as the project, mirroring `projects.rs`. Verified live: a fresh conversion with all 4 workstreams produced them correctly; an empty-array attempt was correctly rejected.
    2. **Change Order re-baselining lost client attribution in the audit trail.** `apply_change_order` (triggered by a client's approval decision) wrote the new quotation, its line items, and the old quotation's supersede-update all as `Actor::System` — so while the `change_order` row itself correctly recorded the client who approved it, every cascading write it caused was anonymous, undermining the traceability goal in `risks.md` risk #4. Fixed in [client_portal.rs](backend/api/src/routes/client_portal.rs): threaded the real `audit::Actor` (the deciding client, or in principle an internal actor if this path is ever reached internally) through `apply_change_order` and `insert_baseline_line` instead of hardcoding `System`. Verified live against three successive change orders: every cascading `quotation`/`quotation_line_item` create and the superseded-quotation `update` now correctly show `actor_client_user_id` matching the change order's own `decided_by`.
  - Deployment note during this milestone: a `tar`-preserved source mtime older than a prior build's Cargo fingerprint caused one rebuild to silently skip recompiling the edited file, so the running server briefly served pre-fix behavior even though the source and a "successful" build both looked correct. Caught by re-querying `audit_log` after the fix and seeing no change — not by trusting the build's exit code. Resolved by touching the file to force a genuine recompile, confirmed by binary mtime becoming newer than the source and the fix behaving correctly. No process change adopted beyond continuing to verify against live behavior, not build/deploy exit codes, which was already this project's standing discipline.
